# 录制标记快捷键修复

2026-10-10，0.2.7 本机人工录制发现 `Ctrl+Alt+M` 被其他应用占用。启动时有提示，但打开工程后状态文字会覆盖提示。初次仅保存一条标记，FT-08 当时未通过；后续备用键补验完成本行有限场景。

0.2.8 将可用快捷键放在录制条的标记按钮内，并让快捷键帮助读取当前注册状态。保留现有圆角、主题和局部实线焦点，按钮文字不会触发窗口拖动。计时区域可以拖动浮条；暂停和收尾期间标记按钮禁用，恢复录制后重新可用。

| 状态 | 行为 |
| --- | --- |
| `Ctrl+Alt+M` 可用 | 按钮显示并使用该键。 |
| 首选键被占用 | 尝试 `Ctrl+Alt+Shift+M`，显示当前备用键，提示说明首选键被占用。 |
| 两组键均被占用或注册发生其他错误 | 按钮显示“快捷键不可用”，点击仍可添加标记；下次录制前重试注册。 |

每次录制写入 `recording-controls.json`，保存可用键及注册结果；`markers.jsonl` 的 `Input` 区分 `button`、`hotkey` 和 `diagnostic`。它们是本机诊断记录，不改变工程格式或标记渲染语义。停止并保存后，工程继续使用原有素材时间映射。

原问题证据：`artifacts/validation/package-0.2.7/recording-markers/initial-result.json`、`hotkey-conflict-startup.txt`。同目录 `probe/result.json` 使用原录制的唯一标记前后两秒进行实际 `ExportEngine` 对照，两份 60 帧 MP4 的解码逐帧 MD5 相同；这只证明该场景下标记不入画，不等同于双输入验收。

验收范围：离屏覆盖首选、冲突、备用、不可用、释放和重试，并检查浅深色录制条布局；实机使用按钮与录制条显示的实际快捷键添加标记，停止、重开核对时间，再完成同工程短区间导出对照。本次用户确认操作序列为按钮1次、备用热键2次，共3条标记。

`artifacts/validation/marker-hotkey-fix/offscreen-v3/result.json` 的94项离屏检查通过，构建0警告0错误。检查覆盖文字和图标均在按钮内、暂停恢复状态、即时计数及按钮文字不会触发拖动；主窗口与录制条均无 HWND。`startup.txt` 记录本机首选键冲突时已成功注册备用键。实机补验见 `recording-proof/desktop-result.json`、`saved-menu-*.jpg`、`reopened-menu-*.jpg`：候选 DLL SHA `AA1A8ED9D46FC5334ABAE2177DFF823311336F97C5403B4FF75D22C6AEFD4AF6`；正常关闭后由最近项目 UI 重开，重开前后项目 SHA `29AE09B6C37D57C778CDADBACAA2DC0BA977502DB7F5C32405022F4A18F80C23` 相同。3条 sourceTime（2.5939237、11.2726287、14.2698502）与录制源日志一致。`recording-proof/probe/result.json` 记录真实 ExportEngine 有标记/无标记短区间导出，380个解码帧像素完全相同，三标记时点均在区间内，原素材和两份输出完整解码退出码0。此为本机测试候选，不是最终 0.2.8 包；FT-08 只在上述首选键冲突、单机备用热键、按钮/热键输入、关闭重开及短区间对照范围内通过。

短区间探针还发现 ExportEngine 向编码器送入381帧，但实际输出解码380帧。三条标记均在导出区间内，故本次 FT-08 有限场景成立；精确到区间尾端帧的范围语义尚未验证。该边界问题待 Media 修复后复验，不能据此宣称亚帧精度或所有短区间均正确。
