# 0.2.13 点击延迟诊断

基线为 `5e490c525099d6a987d7218e0987c293858d347b`。本次增加可关闭的分阶段计时和离屏探针，未把性能修复打进新发行包。运行中的用户程序已核对为0.2.13。

## 已确认原因

1. 跨位置点击的同步部分阻塞界面线程。`SeekTimeline` → `RenderTimelinePreview` → `ScrubFrameDecoder.ReadFrameAsync` 在第一个未完成的 await 之前仍运行于界面线程；旧解码器通过 `MediaTools.StopAsync` 同步执行 `Process.Kill(true)`。受控 FFmpeg 进程实验中，该调用耗时36–68毫秒；只终止受控进程自身的调用耗时约0.23–0.28毫秒。这是进程停止路径的对照，不代表可以全局替换所有终止策略。
2. 新位置经常重建 FFmpeg 进程并重新定位解码。缓存未命中时，倒退或前跳超过0.25秒就会重启。当前 seek 命令没有硬件解码选项。
3. 最近19.28秒录制的关键帧间隔实测为250帧（60fps下约4.17秒）。该素材的 capture-result 指明 FFmpeg ddagrab + h264_nvenc；录制质量参数没有指定 `-g`。同一素材直接读取单帧时，关键帧附近约148–178毫秒，接近下一关键帧前约374–448毫秒，显示定位位置会显著改变解码成本。不得将该周期推广为所有编码器或设备的默认值。

## 主窗口实测

使用用户最近4.58秒和19.28秒的4K60录制，只读加载原工程；项目SHA前后相同。探针经真实时间线输入处理及 MainWindow 订阅发起点击，分别测试保存设置对应的1440档和保留4K源输入的Auto档。没有显示窗口、没有创建HWND，没有导出用户屏幕图片。

1440档结果（排除启动首次GPU初始化）：

| 情况 | 从点击到BitmapSource提交 | 主要成本 |
| --- | --- | --- |
| 相邻/近邻帧 | 约10–19毫秒 | 解码读取约5–9毫秒，GPU合成约1–4毫秒 |
| 已访问且仍缓存的帧 | 约6–8毫秒 | 无新FFmpeg进程 |
| 跨位置/反向随机点击 | 约223–429毫秒 | 解码约212–424毫秒；每次新起1个FFmpeg进程 |
| 随机点击的同步事件处理部分 | 约45–75毫秒 | 进程停止发生在异步方法首次真正挂起之前 |

Auto保留原始4K输入时，本次近邻场景也有约27–79毫秒；整帧数据搬运和合成还有额外成本。当前96MiB像素缓存仅容纳3张4K BGRA帧。冷启动还包括GPU设备等初始化，不应拿首次值当稳态，也不能用同一BitmapSource的复用耗时代替新帧生成耗时。

这里的终点是应用设置 `PreviewImage.Source`；不包含鼠标硬件采样、真实WPF窗口呈现和显示器扫描。5毫秒队列轮询仅用于等待，耗时取自帧提交回调，不将轮询等待加入结果。

## 后续修复顺序

先移出界面线程上的进程启停及解码同步工作，再替换频繁重启的随机寻帧方式并完善帧缓存。新录制的关键帧间隔需要缩短并验证编码质量与体积；这项改变不能单独修好已有的长GOP素材。保留原始画质作为约束，验收分别记录首次、相邻、随机、缓存命中和连续点击的完整提交耗时。

证据根目录：`artifacts/validation/seek-latency-0.2.13/`。`real-19s/` 与 `real-4s/` 包含每次点击、解码进程计数、各阶段耗时及工程SHA；`keyframes.json`、`keyframe-distance.json`、`kill-tree-cost.json` 为独立对照。计时钩子关闭时，13项预览回归通过，见 `regression/`；GPU回归见 `render-regression.log`。

复测命令：`dotnet run --project tests/FrameTrail.App.VisualProbe -c Release -- --preview-latency <新的输出目录> <只读工程路径>`。此命令的测试 Application 明确关闭桌面常驻启动入口。
